# Handoff procedure

Applies whenever a session will be closed, compacted, or handed to another session.

0. In a project that has `~/.claude/projects/<dir>/memory/PROGRESS.md`, steps 1 and 2 are replaced by this one: rewrite PROGRESS.md so `## Now`, `## Open` and `## Next` describe the state as it is (the `Updated:` line from the machine clock, under 80 lines), apply every decision and lesson to `knowledge/`, `decisions/` or the rules directly, and put a finding that cannot be applied yet into `~/.claude/inbox/YYYY-MM-DD-<topic>.md` with `expires: YYYY-MM-DD` as its first line. Its STATE.md is frozen history and gets no new lines. The Stop hook blocks a turn that edited files without rewriting PROGRESS.md.
1. Append to `~/.claude/projects/<dir>/memory/STATE.md` the moment a fact is verified, not at the end - one line each, `- YYYY-MM-DD HH:MM <kind>: <text>` with kind `fact|decision|path|hash|cmd|pending|ruled-out|done|graduated`: paths, hashes, versions, commands that worked, what failed and why, what is still open. A new pending takes the `next id` from the SessionStart context (`pending[p12]: ...`); a settled one is closed by a later line carrying that id (`done[p12]`, `ruled-out[p12]`), or, when it has no id, by a `done` line repeating its first 30 characters. The Stop hook blocks a turn that edited files without adding a line.
2. Graduate from STATE.md: cross-project facts to `~/.claude/knowledge/<topic>.md` with a line in `knowledge/INDEX.md`, why-decisions to `decisions/`, project state to that project's memory or its own docs (`HANDOFF.md`, `docs-design/`, `SCOUT_NOTES.md`) - and its `MEMORY.md` index line. Go through every fact and decision line since the last `graduated` marker, promote the ones still true, then append `- YYYY-MM-DD HH:MM graduated: through <YYYY-MM-DD HH:MM>` with the timestamp of the last line covered. `/handoff graduate` does this step alone. Without a marker nothing is ever archived, and the session start keeps asking for it.
3. A handoff note answers three questions: what is done (with dates), what is pending and whose decision it is, and what a fresh session must read first. Before writing it, the closing session checks its own transcript against it: every issue the user raised, every open thread and every note sent to a peer is either in the note, in PROGRESS.md `## Open` (or a STATE pending line), or explicitly closed - the note is a summary and drops what it does not list.
3a. On resume, the new session does not plan from the note alone: it reconciles the closing session's transcript (its user messages and open threads, read by agents), the injected PROGRESS.md (or STATE's Recent and Open blocks) and any peer notes against the note, records what is missing in PROGRESS.md `## Open` (or as pending lines), and tells the user what was missing before the first plan.
3a. When the work moves to another session, directory or OS (a WSL distro, a renamed repo), the new session's memory
   gets, before it starts: the user's own memories (`user-*`, `feedback-*`, linked from the Windows home memory),
   the PROGRESS/HANDOFF state, and a MEMORY.md line naming the predecessor's
   transcript with the command that reads it on demand -
   `python ~/.claude/scripts/session_digest.py <old transcript.jsonl> | grep -n -i <topic>` - because the reasons
   behind holds and choices live only in the chat. The digest is read into context when needed, never written into
   memory or a record: it carries the user's sentences verbatim, which records must not (rules/context.md).
4. After a compaction, treat the summary as a hint. Re-read the files above and check the filesystem before stating a detail. If the files don't have it, say so rather than reconstructing it.
5. User-facing documents (Japanese) live in `~/.claude/docs/` or the project; everything the user does not read stays English.
